# 技術コンテキスト：Rec-adio

## 現在の技術スタック（v3）

現在のRec-adioは、以下の技術スタックで実装されています：

### バックエンド
- **言語**: Swift 5.6
- **フレームワーク**: Vapor 4（サーバーサイドSwiftフレームワーク）
- **データベース**: MySQL 8.0（FluentMySQLDriverを使用）
- **キューシステム**: Redis（QueuesRedisDriverを使用）

### インフラストラクチャ
- **コンテナ化**: Docker
- **オーケストレーション**: Docker Compose
- **サービス構成**:
  - scheduler: スケジュールジョブを実行
  - recorder: 録音ジョブを実行
  - db: MySQLデータベース
  - redis: Redisキューサーバー

### 録音ツール
- **ffmpeg**: 超A&G+などのストリーミングコンテンツの録音
- **space-dl**: Twitter Spaceの録音
- **yt-dlp**: 将来的なYouTube Liveサポート用

## 技術的課題（v3）

現在のシステムには、以下の技術的課題があります：

1. **複雑な依存関係**:
   - MySQL、Redis、Vaporなど多くの依存関係があり、セットアップや保守が複雑
   - コンテナ化によって緩和されているが、リソース消費が大きい

2. **拡張性の制限**:
   - 新しいプラットフォームを追加するには、コードベースに直接変更が必要
   - プラグインシステムが存在しないため、拡張が困難

3. **クロスプラットフォーム対応の課題**:
   - Swiftはmacとlinuxでの動作は可能だが、パッケージ配布やWindowsサポートに課題がある
   - エンドユーザーへの配布が複雑

4. **リソース効率**:
   - Vaporフレームワークは軽量なアプリケーションとしては過剰なオーバーヘッドがある
   - MySQLとRedisの要件が、単純な録音ツールとしては重い

5. **コマンドラインインターフェースの制限**:
   - 現在のコマンドは限定的で、より柔軟な操作が難しい
   - Vaporのコマンドシステムに依存している

## 新アーキテクチャの技術選定（v4）

v4では、以下の技術スタックを検討します：

### 言語選択

**Go言語**を主要言語として検討する理由：

1. **クロスプラットフォーム対応**:
   - Windows、macOS、Linuxで動作
   - 単一バイナリでの配布が容易

2. **並行処理**:
   - Goroutinesによる効率的な並行処理
   - チャネルによる安全な通信

3. **標準ライブラリの充実**:
   - ネットワーク、ファイル操作、エンコーディングなど基本機能が充実
   - 外部依存を最小限に抑えられる

4. **プラグインシステム**:
   - Go 1.8以降の`plugin`パッケージ
   - または独自のプラグインローダー実装

5. **エコシステム**:
   - CLIツール開発のためのライブラリが充実（cobra, viper）
   - 組み込みデータベースのサポート（BoltDB, BadgerDB）

### データベース

**組み込みデータベース**を採用する理由：

1. **SQLite**:
   - 軽量で信頼性が高い
   - 外部依存なしで動作
   - トランザクションサポート

2. **BoltDB/BadgerDB**:
   - Goネイティブの組み込みKVストア
   - 高速で軽量
   - シンプルなAPI

### APIとプロトコル

コアサービスとクライアント間の通信には、以下のオプションを検討：

1. **RESTful API**:
   - 実装が容易
   - 広く理解されている
   - 標準的なHTTPクライアントで利用可能

2. **gRPC**:
   - 高性能
   - 型安全
   - 双方向ストリーミングをサポート

3. **UNIXソケット/名前付きパイプ**:
   - ローカルシステム内での効率的な通信
   - セキュリティ（ローカルのみ）
   - 低オーバーヘッド

### CLIフレームワーク

コマンドラインツールの実装には、以下のライブラリを検討：

1. **cobra**:
   - 階層的なコマンド構造
   - フラグとオプションの管理
   - ヘルプドキュメントの自動生成

2. **urfave/cli**:
   - シンプルで軽量
   - 柔軟なコマンド定義

### 設定管理

設定ファイルの管理には、以下のライブラリを検討：

1. **viper**:
   - 複数の設定ソースをサポート（ファイル、環境変数、フラグ）
   - 設定の動的な更新
   - 様々なフォーマットをサポート（JSON, YAML, TOML）

### プラグインシステム

プラグインシステムの実装には、以下のアプローチを検討：

1. **Go pluginパッケージ**:
   - 動的ライブラリとしてプラグインをロード
   - 型安全なインターフェース

2. **プロセス間通信**:
   - 別プロセスとしてプラグインを実行
   - 標準入出力またはソケットで通信

3. **スクリプト言語統合**:
   - Lua、JavaScript、Pythonなどのスクリプト言語でプラグインを記述
   - 組み込みインタープリターを使用

## 技術的制約

新アーキテクチャの設計・実装にあたり、以下の技術的制約を考慮します：

1. **後方互換性**:
   - 既存の録音ファイル形式との互換性を維持
   - 移行パスの提供

2. **リソース制限**:
   - 低スペックのマシンでも動作するよう、リソース使用を最小化
   - 長時間の録音でもメモリリークがないよう注意

3. **外部依存**:
   - ffmpeg、space-dl、yt-dlpなどの外部ツールへの依存は継続
   - これらのツールの可用性と互換性を考慮

4. **セキュリティ**:
   - APIアクセスの制限（ローカルのみ、または認証付き）
   - 設定ファイルの保護（特にAPIキーなど）

5. **プラットフォーム固有の課題**:
   - Windowsでのサービス実装
   - macOSでのサンドボックス制限
   - Linuxでのsystemd統合

## 技術的リスク

新アーキテクチャの実装にあたり、以下のリスクを認識しています：

1. **プラグインシステムの複雑さ**:
   - 適切な抽象化レベルの設計が難しい
   - バージョン互換性の管理

2. **外部APIの変更**:
   - Twitter、BiliBiliなどのAPIは頻繁に変更される可能性がある
   - プラグインの迅速な更新メカニズムが必要

3. **クロスプラットフォームの課題**:
   - 各OSの特性に合わせた実装が必要
   - テスト環境の整備

4. **パフォーマンス**:
   - 長時間録音時のメモリ管理
   - 複数の同時録音の処理
